Stability(안정성) 정의

  • Stable: 동일 key 원소들의 원래 상대 순서 보존
  • 예: 정렬
    • Stable → (y가 x 앞, 원래 순서)
    • Unstable → (바뀜)
  • 왜 중요한가: 다중 키 정렬에서는 보조 키(예: 학번)로 먼저 정렬한 뒤 주 키(예: 점수)로 안정 정렬하면, 주 키가 같은 원소들 사이에서만 보조 키의 정렬 순서가 유지된다. 예를 들어 학번 오름차순 정렬 후 점수 오름차순으로 안정 정렬하면, 최종 결과는 점수 오름차순이며 점수가 같은 학생들은 학번 오름차순으로 배치된다. 따라서 안정 정렬은 이전 정렬 결과 전체가 아니라 두 번째 정렬에서 키가 같은 원소들의 상대 순서를 보존한다.

2. Bubble Sort(버블 정렬)

아이디어

  • -th pass에서 -th 최솟값이 -th 위치로 '떠오름'
  • 인접 원소 비교 → 순서 뒤바뀐 쌍 swap
  • Early termination: 한 pass에서 swap 0번 → 이미 정렬됨 → 종료
  • 방향 명시: 이 노트의 구현은 오른쪽에서 왼쪽으로 순회하는 변형으로, pass마다 최솟값이 왼쪽 끝에 확정된다. 일반적인 오름차순 구현은 왼쪽에서 오른쪽으로 순회하며 왼쪽 키가 크면 교환해 pass마다 최댓값이 뒤쪽에 확정된다. 어느 방향이든 교환이 0회인 pass가 나오면 조기 종료할 수 있다.

복잡도

Case 시간
Best (이미 정렬) — early termination
Average / Worst Θ(𝑛²) — 최악의 경우 비교 횟수는 𝑛(𝑛−1)/2번이고 교환 횟수도 최대 𝑛(𝑛−1)/2번
  • Bubble sort는 교환 여부에 따른 조기 종료를 적용했을 때 이미 정렬된 입력에서 첫 pass의 𝑛−1번 비교만 수행하므로 최선 시간은 Θ(𝑛)이다. 입력 순열이 균등하게 주어진다고 가정하면 평균 시간은 Θ(𝑛²)이며, 실제 비교 횟수는 입력과 조기 종료 시점에 따라 달라진다. 최악의 경우 비교 횟수는 𝑛(𝑛−1)/2번이고 교환 횟수도 최대 𝑛(𝑛−1)/2번이므로 최악 시간은 Θ(𝑛²)이다.
  • 용도: 정도 소규모만. 실무 거의 안 씀.

3. Selection Sort(선택 정렬)

아이디어

  • -th pass에서 unsorted 부분의 최솟값 찾아 와 swap
  • pass당 swap 최대 1번 → swap 비용 중요한 상황에 유리

복잡도

  • 비교 횟수는 항상 : best = average = worst
    • 이유: 매 pass마다 나머지 전체를 스캔해 최솟값 탐색
  • Selection sort는 각 pass에서 미정렬 구간의 최솟값을 찾아 현재 위치에 배치하므로 pass당 swap 횟수는 최대 1번이고 전체 swap 횟수는 최대 𝑛−1번이다. 최솟값이 이미 현재 위치에 있다면 swap을 생략할 수 있으므로 실제 횟수는 더 적을 수 있으며, 이미 정렬된 입력에서는 0번도 가능하다. 따라서 비교 횟수는 입력과 무관하게 𝑛(𝑛−1)/2번이지만 swap 횟수는 구현과 입력에 따라 달라진다.

4. Insertion Sort(삽입 정렬)

아이디어

  • -th pass에서 를 이미 정렬된 에 올바른 위치에 삽입
  • 카드 정렬 직관: 한 장씩 뽑아 손에 있는 정렬된 카드에 꽂음

복잡도

  • Best : 이미 정렬된 경우 → 각 원소 비교 1번
  • Insertion sort는 현재 원소를 임시 변수에 저장한 뒤 이미 정렬된 앞부분에서 현재 원소보다 큰 원소들을 오른쪽으로 한 칸씩 이동시키고, 비워진 위치에 현재 원소를 삽입한다. 이미 정렬된 입력에서는 각 원소를 한 번씩 확인하므로 최선 시간은 Θ(𝑛)이며, 입력 순열이 균등하게 주어질 때 평균 시간과 역순 입력에서의 최악 시간은 모두 Θ(𝑛²)이다. 이때 기본 shift 구현은 원소 이동을 수행하며 swap을 필수로 사용하지 않는다. 인접 원소를 반복 교환하는 변형에서는 평균·최악 swap 횟수가 Θ(𝑛²)이 될 수 있다. 같은 키를 가진 기존 원소를 새 원소 뒤로 밀지 않으면 안정성을 유지한다.

실전 가치

  • Insertion sort는 시간 복잡도가 평균·최악 Θ(𝑛²)이지만 구현이 단순하고 반복문의 상수 비용이 작기 때문에 작은 부분배열에서는 Merge sort나 Quick sort보다 빠를 수 있다. 따라서 하이브리드 정렬 구현에서는 재귀적으로 처리할 부분배열의 크기가 일정 임계값 이하가 되면 Insertion sort로 전환하기도 한다. 이 임계값은 이론적으로 15로 고정된 것이 아니라 구현·하드웨어·입력 특성에 따라 달라지며, 실제 성능 측정을 통해 정하는 값이다.
  • → Merge/Quick sort에서 recursion base로 사용 (hybrid 기법)

5. Bucket Sort (Non-Comparison)

아이디어

  • 키 값으로 직접 index 접근 → 비교 없이 분류
  • Phase 1 (Scatter): 각 원소를 key에 해당하는 bucket에 배치
  • Phase 2 (Gather): bucket 순서대로 꺼내 연결

복잡도

  • Scatter:
  • Gather: (bucket 수 고려)
  • Total:

적용 조건

  • Key 범위 이 작을 때 효율적
  • 적용 조건: 정수 키 직접 인덱싱 방식의 Bucket Sort는 n개의 원소를 처리하고 N개의 bucket을 초기화·순회하므로 시간 복잡도가 O(n+N)이다. N=O(n)이면 전체 시간도 O(n)이므로 효율적일 수 있다. 반면 N이 n에 비해 매우 크게 증가하면 빈 bucket의 초기화·순회 비용이 지배적이 되어 비효율적일 수 있다. 따라서 N>n이라는 조건만으로 비교 정렬보다 반드시 느리다고 단정할 수 없으며, 실제 선택은 N의 크기, 메모리 사용량, 다른 정렬 알고리즘의 비용을 함께 고려해야 한다.

정수 키 직접 인덱싱 Bucket Sort의 안정성: 정수 키가 [m, m+N−1] 범위에 있다면 각 원소를 bucket[key−m]에 배치할 수 있다. 이때 원소를 원래 입력 순서대로 각 bucket의 끝에 추가하고, gather 단계에서도 bucket 내부 원소를 삽입된 순서대로 출력하면 같은 키의 상대 순서가 보존되므로 안정 정렬이다. 반대로 bucket 내부에서 입력 순서를 보존하지 않는 구현은 안정성을 보장하지 않는다.

Q1Float key(예: 0.78, 0.12, …)도 bucket sort가 가능한가?
힌트

bucket sort는 key의 값 범위를 구간으로 나누는 방식이다.

정답
  • 정답: 가능하다. 모든 키가 [0,1) 범위에 있으면 해당 구간을 𝑘개의 bucket으로 분할하고, 각 키 𝑥를 인덱스 ⌊𝑘𝑥⌋에 해당하는 bucket에 넣는다. 그다음 각 bucket 내부를 Insertion sort 등의 방법으로 정렬하고 bucket을 인덱스 오름차순으로 연결하면 전체 배열이 정렬된다. 시간 복잡도: 𝑛개의 키가 독립적으로 균등분포에서 추출되고 bucket 수가 𝑘=Θ(𝑛)이면 각 bucket에 들어가는 원소 수가 평균적으로 작아지므로 Insertion sort를 이용해도 전체 기대 시간은 𝑂(𝑛)이다. 반대로 원소들이 한 bucket에 집중되면 내부 삽입 정렬의 비용 때문에 최악 시간은 𝑂(𝑛²+𝑘)가 된다. 핵심 구별: 정수 키를 bucket 인덱스로 직접 사용하는 방식의 𝑂(𝑛+𝑁) 복잡도와 실수 구간 분할 방식의 기대 𝑂(𝑛) 복잡도는 적용 조건이 다르다.
Q2Bucket sort가 느려지는 경우는?
힌트

bucket의 개수와 분포 균일성이 성능을 좌우한다.

정답

개념은 힌트 참고.

  • Bucket Sort의 구현 방식에 따라 성능 저하 조건이 다르다. (1) 정수 키 직접 인덱싱 방식: 키 범위의 크기 N이 n에 비해 매우 크면 빈 bucket의 초기화·순회 비용이 커져 O(n+N) 시간이 지배된다. 각 bucket에 원소를 상수 시간으로 추가하고 그대로 출력하는 구현이라면, 원소가 특정 bucket에 집중되더라도 점근적 시간 상한 O(n+N)은 변하지 않는다. (2) 실수 키 구간 분할 방식: 각 bucket 내부를 Insertion Sort로 정렬한다면 입력 분포가 편중되어 한 bucket에 많은 원소가 몰릴 때 정렬 비용이 증가한다. 최악에는 한 bucket에 n개의 원소가 모여 전체 시간이 O(n²+k)가 된다. 따라서 두 방식의 복잡도를 분석할 때는 각각 키 범위의 크기와 bucket 내부 원소 수의 분포를 구별해야 한다.

6. Merge Sort(병합 정렬)

Divide & Conquer

  1. Divide: 배열을 반으로 분할
  2. Conquer: 각 반을 재귀적으로 정렬
  3. Combine: 두 정렬된 리스트를 merge

Merge 연산 자체

  • 두 정렬 리스트 를 merge
  • Merge 연산은 이미 정렬된 두 리스트의 현재 원소를 두 포인터로 비교하여 키가 작은 원소를 출력에 추가한다. 두 원소의 키가 같은 경우에는 원래 배열에서 앞에 있던 왼쪽 부분배열의 원소를 먼저 출력해야 동일 키의 상대 순서가 보존된다.
  • 한쪽 리스트가 소진되면 다른 쪽 리스트의 남은 원소들을 기존 순서대로 출력에 연결한다. 이 동률 처리 규칙을 모든 병합 단계에서 지키면 Merge sort는 안정 정렬이며, 길이가 각각 𝑛, 𝑚인 두 리스트의 병합 시간은 𝑂(𝑛+𝑚)이다.

7. Quick Sort(퀵 정렬)

Divide & Conquer (Partition 기반)

  1. Pivot(피벗) 선택
  2. Partition: pivot 기준 3 그룹
    • Left: key < pivot
    • Pivot
    • Right: key ≥ pivot
  3. 재귀: left, right 각각 정렬
  4. Combine: Quick sort에서 sorted(L) + pivot + sorted(R)은 최종 결과의 논리적인 순서를 나타내는 표현이다. 제자리 Quick sort는 partition 과정에서 pivot을 최종 위치에 배치한 뒤 그 양쪽 부분배열을 같은 배열 안에서 정렬하므로 별도의 concat 연산이 필요하지 않으며, 이 의미에서 combine 단계의 추가 작업은 𝑂(1)이다. 반면 별도의 리스트들을 실제로 복사하여 연결하는 구현에서는 결합에 𝑂(𝑛) 시간과 추가 저장 공간이 필요할 수 있다.

Partition 방법

양방향 In-place Partition — 첫 원소를 pivot으로 사용하는 구현

  • 배열의 현재 정렬 구간을 A[𝑙𝑜..ℎ𝑖]라 하고 pivot 값 𝑝=A[𝑙𝑜]를 선택한다. 왼쪽 포인터를 𝐿=𝑙𝑜+1, 오른쪽 포인터를 𝑅=ℎ𝑖로 초기화한다.
  • 왼쪽 포인터 𝐿은 배열 범위 안에서 A[𝐿]<𝑝인 원소들을 건너뛰며 오른쪽으로 이동하고, A[𝐿]≥𝑝인 원소를 만나면 멈춘다.
  • 오른쪽 포인터 R의 이동 및 종료 조건: 오른쪽 포인터 R은 R이 lo보다 큰 동안, 현재 원소 A[R]의 키가 pivot 값 p 이상이면 왼쪽으로 한 칸씩 이동한다. A[R]의 키가 p 미만인 원소를 만나거나 R이 lo에 도달하면 이동을 멈춘다. R이 lo에 도달했다면 pivot 자신을 다시 검사하여 R을 더 감소시키지 않는다. 따라서 오른쪽 포인터 R은 항상 lo 이상의 인덱스를 유지한다. 정렬 구간에 pivot보다 작은 원소가 하나도 없는 경우에는 R이 lo에서 종료한다. 이후 두 포인터의 위치를 비교한다. L이 R보다 작으면 A[L]과 A[R]을 교환하고, L을 한 칸 증가시키며 R을 한 칸 감소시킨 뒤 탐색을 반복한다. L이 R 이상이면 탐색을 종료하고 A[lo]와 A[R]을 교환하여 pivot을 인덱스 R에 배치한다. 특히 R이 lo인 경우에는 pivot을 자기 자신과 교환하므로 pivot 위치는 변하지 않는다. 이 과정을 마치면 pivot 왼쪽에는 pivot보다 작은 키만 존재하고, 오른쪽에는 pivot 이상의 키만 존재한다. 이후 pivot을 제외한 왼쪽 부분 배열과 오른쪽 부분 배열을 각각 재귀적으로 정렬한다.
  • 중복 키가 많으면 분할이 심하게 불균형해질 수 있으며, 이 경우 세 구간(key < pivot, key = pivot, key > pivot)으로 나누는 3-way partition을 고려할 수 있다.
  • 추가 메모리 거의 없음 → cache friendly

실전 선택 기준

  • Quick sort: 평균 시간 복잡도가 𝑂(𝑛 log 𝑛)이고 제자리 partition에서 좋은 메모리 접근 지역성을 보이는 경우가 많아 일반적인 배열 정렬에서 효율적인 선택이 될 수 있다. 그러나 실제 성능은 pivot 선택 전략, 입력 분포, 구현 최적화와 하드웨어 특성에 따라 달라지므로 항상 가장 빠른 정렬 알고리즘이라고 단정할 수는 없다. 안정성이 필요한 경우에는 stable Merge sort를 고려하고, 최악 시간 𝑂(𝑛 log 𝑛) 보장과 𝑂(1) 추가 배열 공간이 중요한 경우에는 Heap sort를 고려할 수 있다. 또한 실제 라이브러리에서는 여러 알고리즘을 결합한 하이브리드 정렬을 사용할 수 있으므로 요구사항과 구현 특성에 따라 선택해야 한다.
  • Merge sort: worst-case 보장 + stable 필요 시 (예: 외부 정렬, linked list)
  • Heap sort: 실시간 시스템 (worst 보장 + 공간)
    • quick sort는 worst 이라 실시간엔 위험

Quick space 주의: Quick sort의 일반적인 재귀 구현은 균형 잡힌 분할이 이루어질 때 호출 스택 깊이가 𝑂(log 𝑛)이지만, 극단적으로 불균형한 분할이 반복되면 스택 깊이가 𝑂(𝑛)까지 증가할 수 있다. 최악의 경우에도 추가 스택 공간을 𝑂(log 𝑛)으로 제한하려면 매 단계에서 크기가 더 작은 부분배열만 재귀 호출하고 더 큰 부분배열은 현재 함수의 반복문으로 처리하는 tail-recursion elimination을 적용해야 한다. 단순히 작은 쪽을 먼저 재귀 호출하는 것만으로는 이러한 최악 공간 상한이 보장되지 않는다. 따라서 기본 Quick sort의 추가 공간은 평균 𝑂(log 𝑛), 최악 𝑂(𝑛)이며, 위 최적화를 적용한 구현에서는 최악 스택 공간도 𝑂(log 𝑛)이다.

Quick의 cache 이점

  • Quick sort는 제자리 partition 과정에서 같은 배열의 비교적 인접한 원소들을 반복적으로 접근하기 때문에 좋은 공간 지역성(cache locality)을 보이는 경우가 많으며, 이러한 메모리 접근 특성이 실제 성능에 유리하게 작용할 수 있다.
  • 반면 배열 기반 Merge sort는 보조 버퍼가 필요하지만 병합 과정에서 원소들을 순차적으로 읽고 쓰므로 캐시 효율이 반드시 나쁜 것은 아니다. 두 알고리즘의 실제 cache miss 횟수와 실행 성능은 배열 크기, 메모리 계층 구조 및 구현 방식에 따라 달라진다. 여기서 사용하는 개념은 cache coherence가 아니라 cache locality이다.

실수 키 구간 분할 Bucket Sort의 시간 복잡도는 k개의 bucket을 초기화하고 각 bucket 내부를 Insertion Sort로 정렬하는 구현을 기준으로 한다. 최선 시간은 O(n+k)이며 기대값으로 표현하지 않는다. n개 키가 독립적인 균등분포를 따를 때 평균 시간 상한은 O(n+k+n²/k)이고, k=Θ(n)이면 O(n)으로 단순화된다. 입력이 특정 bucket에 집중되면 최악 시간은 O(n²+k)가 된다.

* float key 변형처럼 bucket 내부 정렬(insertion sort)이 필요한 경우, 한 bucket에 몰리면 내부 정렬 비용 Θ(n²)이 지배. 정수 key 직접 index 버전은 worst에도 O(n+N).

이 표의 Best, Avg, Worst는 각각 최선·평균·최악 입력에서의 점근적 시간 상한 𝑂(·)을 나타내며, Space는 입력 배열을 제외한 추가 공간의 점근적 상한을 나타낸다. 𝑛은 정렬할 원소의 개수이고, 𝑁은 정수 키를 직접 인덱싱하는 방식에서 사용되는 키 범위의 크기이며, 𝑘는 실수 키 구간 분할 방식에서 사용하는 bucket의 개수이다. 표의 1, 𝑛, 𝑛 log 𝑛, 𝑛² 표기는 각각 𝑂(1), 𝑂(𝑛), 𝑂(𝑛 log 𝑛), 𝑂(𝑛²)을 의미한다. Quick sort의 Space는 기본 재귀 구현에서 평균 𝑂(log 𝑛), 최악 𝑂(𝑛)이며, 작은 부분배열만 재귀 호출하고 큰 부분배열을 반복문으로 처리하도록 최적화하면 최악에도 𝑂(log 𝑛)으로 제한할 수 있다. Bucket sort는 정수 키 직접 인덱싱 방식과 실수 구간 분할·내부 정렬 방식을 구별하여 별도 행으로 표시한다.

  • Comparison sort의 하한: 모든 비교 기반 정렬 알고리즘에는 최악 Ω(𝑛 log 𝑛)의 하한이 존재한다. 입력 순열이 균등하게 주어진 경우 평균 비교 횟수에도 Ω(𝑛 log 𝑛) 하한이 성립하지만, 개별 알고리즘의 최선 시간까지 반드시 Ω(𝑛 log 𝑛)이어야 하는 것은 아니다.
  • Bucket sort와 Radix sort는 키끼리의 대소 비교만으로 정렬 순서를 결정하지 않기 때문에 비교 정렬의 Ω(𝑛 log 𝑛) 하한이 직접 적용되지 않는다. 다만 선형 시간에 정렬할 수 있는 조건은 알고리즘마다 다르다. 정수 키 직접 인덱싱 Bucket sort는 키 범위 크기가 𝑁일 때 𝑂(𝑛+𝑁) 시간이 걸리고, 실수 구간 분할 Bucket sort는 적절한 bucket 수와 독립적인 균등분포 가정 아래 기대 𝑂(𝑛) 시간이 가능하다. Radix sort는 키를 𝑑개의 자릿수로 표현하고 각 자리마다 기수 𝑏의 안정적인 Counting sort를 수행하면 𝑂(𝑑(𝑛+𝑏)) 시간이 걸리며, 𝑑=𝑂(1)이고 𝑏=𝑂(𝑛)인 조건에서는 𝑂(𝑛) 시간이 가능하다. Radix sort의 이 시간 상한은 키 분포가 균등하다는 가정을 필요로 하지 않는다.
